# /api/v1/db — direct database access

Bearer-token SQL access to the production database, for the owner's terminal and trusted agents. Mint a token at
`/admin-dashboard/api-tokens` with scope **`db:read`** (SELECT) and/or **`db:write`** (INSERT / UPDATE / DELETE).
A `*` token does **not** include these scopes; they must be named. Store the token in the macOS Keychain, never in `.env`:

```bash
security add-generic-password -U -s exam-db-token -a "$USER" -w '<token>'
npm run db:prod -- schema User
npm run db:prod -- query 'SELECT id, email, "emailVerified" FROM "User" WHERE email = $1' someone@example.com
npm run db:prod -- exec 'UPDATE "User" SET name = $1 WHERE id = $2' 'Jane Tan' <id> --dry-run   # then without --dry-run
```

| Method & path | Scope | Body / query | Returns |
|---|---|---|---|
| `GET /api/v1/db/schema?table=` | `db:read` | — | `tables{ name: { columns[{name,type,nullable,writable}], hidden[], writable } }` |
| `POST /api/v1/db/query` | `db:read` | `{ sql, params?: [], limit?: 200 (≤1000) }` | `{ rows, rowCount, truncated, ms }` |
| `POST /api/v1/db/execute` | `db:write` | `{ sql, params?: [], maxAffected?: 100 (≤10000), dryRun?: false }` | `{ verb, affected, committed, dryRun, rows (RETURNING), ms }`; 409 and nothing changed when more rows than `maxAffected` |

How it is kept safe ([src/lib/db-api.ts](../src/lib/db-api.ts)):

- Each call is one transaction under `SET LOCAL ROLE app_db_reader` / `app_db_writer` (NOLOGIN roles the app re-grants
  on first use after every deploy, from `information_schema`), with a statement timeout; queries are also `READ ONLY`.
  Postgres refuses anything the role lacks — the text checks below are only a second layer.
- **Never readable**: `User.passwordHash`, `User.totpSecret`, `Account` OAuth tokens, `ApiToken.hashedToken`,
  `WebhookSubscription.secret`, `OtpCode.codeHash`, `Attempt.guestToken`, the `Setting` table. So `SELECT *` and
  whole-row reads on those tables fail — name the columns.
- **Never writable**: those columns, `User.role` (use admin → Admins), and the `Setting`, `ApiToken`, `AdminLog` and
  `_prisma_migrations` tables. No DDL (schema changes go through Prisma migrations).
- One statement per call (pass values as `$1…` params), no SQL comments, no admin/file/sleep functions,
  UPDATE/DELETE need a WHERE.
- Every call is audited in AdminLog (`db.query`, `db.execute`, `db.execute_dry_run`) as the token's admin with
  `via: 'api'`, with the SQL. 120 queries / 30 writes per minute per token.

Writes bypass the app's own logic (fulfilment, emails, invoices, audit entries the dashboard would make). Prefer the
admin dashboard or a purpose-built endpoint for anything with side effects; ids are cuids generated by the app, so an
INSERT must supply `id` (and `updatedAt` where the column has no default).
