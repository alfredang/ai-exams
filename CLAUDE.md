## Architecture

**Theme & design tokens**: the site is light by default — the `<head>` init script only applies `dark` when `localStorage.theme` is `'dark'`, or `'system'` (set from the user settings picker) and the OS prefers dark. **Light = light blue** (light-blue page and alternating `bg-canvas` bands, white cards, blue-tinted borders, navy text); **dark = premium deep navy** (navy page with a fixed blue radial glow, raised navy cards, brighter `brand-500` buttons with `shadow-glow`). Every neutral on the site is `slate`, so the theme lives in the blue-tinted `slate` ramp in `tailwind.config.ts` — keep its lightness order (50 lightest → 950 darkest) or light/dark class pairs lose contrast. `page`/`canvas`/`ink`/`muted`/`line` are CSS-variable tokens in `globals.css` that switch under `.dark`; `navy` is the fixed test-centre chrome. `globals.css` also lifts bare `text-slate-500…900` in dark mode (explicit `dark:text-*` still wins), so an element with `bg-white` and grey text **must** carry its own `dark:bg-*`. `.light-scope` pins light tokens and text colour — the exam runner and the hero's exam window use it so they stay a light test-centre screen in both themes; inside them use fixed light classes, not the shared `.btn-*` (those carry dark variants). Fonts are Archivo (`font-display`, h1–h3), IBM Plex Sans (`font-sans`) and IBM Plex Mono (`font-mono`, `.eyebrow` labels). The homepage hero is the animated `components/hero-exam-visual.tsx` (no hero image; `/hero.webp` remains only as the social-card fallback).

Single Next.js App Router app — server logic (payment webhooks for PayPal/Stripe/HitPay, Auth.js, Claude SSE, voucher PDF) lives in route handlers. The brief mentioned Vite as an alternative; we chose Next.js for the unified server.

- `/api/mobile/*` — REST surface for the native iOS/Android apps (auth, catalog, attempts, library, account). Don't rename these without coordinating an app release; changes are additive only. The apps (iOS `alfredang/aiexamapp`, Android `alfredang/aiexamapp_android`) are **only for customers to take the practice exams they already own, on the move** — no purchasing, no catalog, no admin. They use:
  - **Email-code sign-in** (no CAPTCHA on native, so per-IP caps): `POST /api/mobile/auth/code/request` `{ email, purpose: LOGIN|REGISTER, name? }` (LOGIN never reveals whether the account exists; REGISTER needs a full name, screens new domains and creates the account unverified with no password, 409 if already verified) → `POST /api/mobile/auth/code/verify` `{ email, code, purpose }` → `{ token, user }` and marks the inbox verified. Password sign-in (`auth/login`) stays for App Review demo accounts.
  - **Google sign-in** (browser handoff, reuses the web NextAuth Google client — no native Google client ids): the app opens `GET /api/mobile/auth/google/start?code_challenge=<S256>&state=` in an ephemeral ASWebAuthenticationSession → NextAuth Google → `GET /api/mobile/auth/google/complete` redirects to `aiexams://auth/callback?code=…&state=` (or `?error=`) with a 2-minute HMAC handoff code bound to the PKCE challenge (`issueHandoffCode()` in [src/lib/mobile-auth.ts](src/lib/mobile-auth.ts)) → `POST /api/mobile/auth/google/exchange` `{ code, verifier }` → `{ token, user }`. The token never appears in a URL.
  - **Sign in with Apple** (iOS, required by App Store 4.8 alongside Google): `POST /api/mobile/auth/apple` `{ identityToken, nonce, fullName? }` verifies the token with `jose` against Apple's JWKS (`aud` = bundle id `com.tertiaryinfotech.aiexams`, `nonce` claim = SHA-256 hex of the raw nonce), then finds the user by `Account(provider 'apple', sub)`, else by Apple's verified email (linking it), else creates a verified account → `{ token, user }`. `DELETE /api/mobile/account` also deletes the user's `Account` rows so Google/Apple start fresh after deletion.
  - `GET /api/mobile/attempts` — exam history from `getAttemptHistory()` (attempts newest first + per-exam best/average/latest/domains; `examId` is the pool exam, matching `library`).
  - `GET /api/mobile/attempts/[attemptId]` — same per-attempt option order as the web runner (`optionsForAttempt`), plus `remainingSec` (Exam mode clock from `expiresAt`), `selectCount` (MULTI) and `steps` (ORDERING, `sequencingSteps` order; the answer is the sequence of step ids); correct/explanation/references only after submit.
- `/api/v1/*` — bearer-token API for agents/partners, authed by `requireApiToken(req, scope)` in [src/lib/api-v1.ts](src/lib/api-v1.ts) (tokens from `/admin-dashboard/api-tokens`; `Authorization: Bearer` or `X-API-Key`; the token must carry the scope or `*`, and its creator must still be an active ADMIN — mutations are audited as that admin with `via: 'api'`). Outside the proxy matcher on purpose (no session). `GET /api/v1/practice-exams?q=` and `GET|POST|DELETE /api/v1/assignments` (scope `assign:practice-exams`) grant/remove `ADMIN_GRANT` on the pool exam; DELETE never touches paid tiers. Exams resolve by code, product slug or id via `resolvePracticeExam()`. ### Auth & RBAC (subtle)
- **Two NextAuth Credentials providers** in [src/lib/auth.ts](src/lib/auth.ts): id `password` and id `otp`. The OTP provider verifies a `LOGIN` code from `OtpCode` (no FK to user) and signs in an existing user only — accounts are created by the `REGISTER`/`TEASER_GATE` branches of [api/otp/verify](src/app/api/otp/verify/route.ts), OAuth, mobile register, or an admin.
- **Edge-safe split**: middleware imports [src/lib/auth.config.ts](src/lib/auth.config.ts) (no providers, no Prisma, no argon2) — argon2 has `node:crypto` imports that webpack edge cannot bundle. The full config in [src/lib/auth.ts](src/lib/auth.ts) extends it with the heavy providers.
- **OTP table has no FK** ([prisma/schema.prisma](prisma/schema.prisma) `OtpCode`) so codes can be issued before the user exists — required for the teaser→signup flow. Purposes: `LOGIN | REGISTER | RESET | TEASER_GATE`.
- OTP requests now return a delivery error when all email transports fail, and the unsent code is invalidated. Do not report that a code was sent when `sendOTPEmail()` fails.
- Email logs deliberately omit `payloadVars` for OTP templates so plaintext codes are not retained outside the hashed `OtpCode` record.
- The `20260914010000_redact_otp_email_logs` migration removes plaintext OTP template variables from older email-log rows. GDPR user-data export omits password hashes and TOTP secrets and redacts any OTP template variables still present.
- **Anti-spam / anti-fraud guardrails** — keep all of these when touching signup or login:
  - **CAPTCHA**: Cloudflare Turnstile on every `/api/otp/request` (signup, email-code login, reset, teaser gate) via [src/lib/captcha.ts](src/lib/captcha.ts) + the `useCaptcha()` hook in [src/components/captcha.tsx](src/components/captcha.tsx). Keys are runtime settings (`TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY`, admin → Settings → Security); the check is a no-op until both are set, and fails closed if Cloudflare is unreachable. Tokens are single-use, so follow-up LOGIN codes after a REGISTER/TEASER_GATE verify are issued server-side via `sendLoginCode: true` on `/api/otp/verify` — don't reintroduce a second client-side `/api/otp/request` call there.
  - **Email screening** ([src/lib/email-guard.ts](src/lib/email-guard.ts)): new accounts (REGISTER/TEASER_GATE for unknown emails, mobile register) are refused for disposable domains or domains with no MX record. Existing users are never screened.
  - **No mail to non-accounts**: `issueOtp()` silently skips LOGIN/RESET codes for emails without an active account (same response either way, so no account enumeration).
  - **Client IP** for rate-limit keys comes from `clientIp()` ([src/lib/client-ip.ts](src/lib/client-ip.ts)) — the right-most `X-Forwarded-For` entry, appended by Coolify's proxy. Never key on the raw header; a spoofed prefix gives a fresh bucket per request. If a CDN is ever put in front, revisit this.
  - Rate limits (failures-only for sign-in): OTP request 20/h/IP + 3/h/email (email key ignores `+tag` and Gmail dots via `rateLimitEmailKey()`); OTP verify 20/h/IP + 10/h/email; password and email-code sign-in (web + mobile) 20/15 min/IP + 10/15 min/email failures plus 60/15 min/IP overall. A one-time code is burned after 5 wrong guesses (`OtpCode.attempts`).
  - **Bots**: forms send a honeypot field and form-open time via `captcha.fields()`; `/api/otp/request` requires `application/json` and quietly returns `{ok:true}` without mailing for honeypot hits or submits under 2s.
  - **Mobile register** (`/api/mobile/auth/register`) no longer marks the email verified: it returns 202 `{ needsVerification: true }` and emails a REGISTER code; the app finishes with `POST /api/otp/verify` (`purpose: REGISTER`, `newPassword`) and then `/api/mobile/auth/login`, which returns 403 `{ needsVerification: true }` for unverified accounts. A first verified sign-in (OTP, OAuth) clears any password set before verification (`markInboxVerified()`).
  - OAuth sign-in marks `emailVerified` on every sign-in where it is null (not only new users), so admin-created accounts that later link Google/GitHub count as verified.
- [src/proxy.ts](src/proxy.ts) (the middleware; Next now calls this "proxy") gates `/admin-dashboard/*`, `/api/admin/*`, `/user-dashboard/*` — anonymous users bounce to `/login?next=…`, non-admins on admin paths bounce to `/`. Admin pages/APIs also re-check `role === 'ADMIN'` server-side.
- **Admin look (light theme)**: `AdminChrome` wraps the admin in `.admin-scope`; in light mode `globals.css` renders bare `text-slate-400` / `text-slate-500` one step darker inside it (contrast on white and on the light-blue page), so don't hand-pick paler greys. Use the shared classes instead of hand-written strings: `.admin-h1` (or `PageHeader`), `.admin-label` (uppercase section/KPI labels), `.admin-thead` (every table header, `DataTable` included), `.admin-link`, `.btn-sm-primary` / `.btn-sm-quiet`, `Badge` / `StatusBadge`, and `StatCard` (`components/admin/stat-card.tsx`) for KPI tiles — its accent border uses `!border-l-*` because `.dark .card` would otherwise override it. Admin accents are `brand-*`, never Tailwind's default `blue-*`. Buttons on amber use dark text (`bg-amber-400 text-amber-950`), not white.
- **Admin speed**: list pages fetch count + rows in one `Promise.all` (re-reading rows only when the requested page is past the end), never `include: { user: true }` without `omit: { passwordHash: true, totpSecret: true }`, and leave `paypalPayload` / `providerPayload` out of lists. Per-row totals come from `groupBy` on an indexed column, not relation `_count` on Attempt/Order. Filter dropdown values use `groupBy`, not `distinct` (Prisma de-duplicates `distinct` in memory). The columns admin pages sort and filter on are indexed (migration `20261116090000_admin_speed_indexes`) — add an index when a new list sorts on a new column. `src/app/admin-dashboard/loading.tsx` is the skeleton shown on every admin navigation.
- **Admin UI conventions**: `DataTable` columns take `hideBelow: 'lg'|'xl'|'2xl'` (drop secondary columns so row actions stay on screen) and `sticky: true` (pins the actions column from `lg`). Admin money uses `formatMoney()` (zero is `$0.00`); `formatPrice()` is storefront-only (zero reads "Free"). Admin text floor is 11px (`text-[11px]`); nothing smaller. Below `lg` the admin sidebar is an off-canvas drawer opened by the Menu button in `admin-chrome.tsx`. Admin search and the notification bell live in the site top header (`components/admin/header-tools.tsx`, lazy-loaded by `nav.tsx` with `next/dynamic` on `/admin-dashboard/*` so public pages don't download them; the bell polls every 60s only while the tab is visible), not in the sidebar. Search is an inline box (`components/admin/admin-search.tsx`, ⌘K focuses it) whose results drop down beneath it as you type — no modal palette. Below `md` the dropdown is `fixed` inside the header; the header's `backdrop-blur` makes it the containing block, so the dropdown spans the header width.
- **In-memory rate limiter** ([src/lib/ratelimit.ts](src/lib/ratelimit.ts)) does NOT survive restarts and does not work across replicas. Replace with Redis/Upstash before scaling out.
- Password hashing uses **argon2id** (deviates from spec's bcrypt — argon2id is OWASP-recommended).

### Exam runtime — the most subtle part
- [components/exam-runner.tsx](src/components/exam-runner.tsx) is one client component for both modes. Mode is a prop. Differences: PRACTICE reveals correctness/explanation/references immediately (references rows are historically either URL strings or `{url,label}` objects — handle both); EXAM persists each answer via a debounced call to `/api/attempts/answer`, auto-saves every 15s, and auto-submits at timer 0 with a "Time's up" overlay.
- The runner is a **full-viewport test-centre shell** (fixed overlay above the site nav, body scroll locked, `.light-scope` so it stays light in dark mode): navy title bar with Time Remaining and "N of M", a slim tool strip (answered count, save state, answer-sheet toggle), and the question card laid out like the mock-exam booklet — "Question N of M" with a **Mark for review** toggle at its top-right, the options, then full-size **Previous / Next** and a primary **End exam** button inside the card. In PRACTICE an answer-sheet panel sits to the right, and signed-in practice attempts get a **Switch to Exam mode** title-bar button (saves, then `startFromDashboard` with EXAM). **EXAM mode runs like the live test**: no answer sheet, no Submit and no Review Screen button until the candidate reaches the end (`reachedEnd`; true on resume when every question is answered) — Next on the last question reads "Review Screen" and opens it. The Review Screen shows Completed / Flagged for review (+ Incomplete when any) counts, in-card **Review flagged questions (N)** / Review incomplete / Review all / **Submit Exam** buttons, and a one-column Question · Status · Flagged table; its navy bottom bar has **Review All**, **Review Flagged**, Review Incomplete (only while some are incomplete), Review Incorrect (PRACTICE) and **Submit Exam**. Each Review walk visits only those items, then returns to the Review Screen. Exam mode hides the question's domain until results, like the live exam. Right-click strikes out an option (visual only, never saved). "Save & exit" flushes autosave and leaves via `exitHref` (set in `exam-shell.tsx`; signed-in users go back to `/user-dashboard`, where the badge offers Resume); the timer keeps running server-side.
- **Leaving the runner is always a full page load** (`window.location.assign` after submit and on Save & exit), never `router.push`. A deploy during a 2-hour exam replaces the JS chunks an open tab needs for a client navigation; on 16 Nov 2026 a whole CCAR-F class sat on "Submitting…" with their scores already saved. Don't switch these back to the router.
- **Every submit goes through `finalizeAttempt()`** ([src/lib/finalize-attempt.ts](src/lib/finalize-attempt.ts)) — web and mobile submit routes and the expired-exam sweep. It scores from the saved responses, stamps `submittedAt` with an `updateMany … submittedAt: null` guard, and the one call that closes the attempt emails the candidate the `EXAM_RESULT` template (`sendExamResultEmail()` in `mail.ts`: score, PASS/FAIL, score by domain, the answer-review PDF attached; signed-in, non-teaser attempts with at least one answer; never awaited, a mail failure never fails a submit). **An Exam-mode attempt whose timer ran out unsubmitted** (tab closed, asleep, Save & exit) is scored as at `expiresAt`, 90 s after expiry, by `finalizeExpiredAttempts()` — called at the top of `getAttemptHistory()` — and by `/exam/[attemptId]`, which redirects it to the report instead of a dead 0:00 runner. One with no answers is left unscored and shows as "Time expired" in the history. `buildAttemptReport()` in the same file feeds both the PDF download route and the email attachment. Manual catch-up: `POST /api/admin/attempts/result-email` `{ attemptIds: [≤50] }` (ADMIN, audited `attempt.result_email`) re-sends the report for submitted, signed-in, non-teaser attempts. The same catch-up for agents/CLI: `POST /api/v1/attempts/result-emails` (scope `results:email`; a `db:write` token is also accepted), both through `resendResultEmails()`.
- Ending goes through the **End Exam dialog** (answered/unanswered/flagged counts, tap-to-jump chips) — EXAM mode disables the submit button until every question is answered; PRACTICE can finish anytime. Keyboard: ←/→ navigate, F flags. Don't reintroduce `alert()`/`confirm()` here.
- `/results/[attemptId]` follows the mock-exam score report: big `correct / total` with a large **PASS / FAIL** badge (attempt rows and the PDF say Pass / Fail too; there is no share section), a 4-band readiness scale scaled from the 15-question table (`readinessBands()`), domains sorted weakest-first with a NEXT STUDY TARGET tag at 2+ misses, and a **Review your answers** list filtered by `?view=missed|flagged` — every option is shown in the seeded per-attempt order with the correct one green and a wrong pick red, then the answer-key box led by an **Exam domain** chip, then WHY. The report has ONE action bar under the readiness scale — **Retake exam** (primary; a server action, teasers POST to the teaser route instead; creates a new attempt in the same mode, falling back to the exam page without an entitlement), **Review questions and answers (N)** (jumps to `#review`, the answer list further down the same page), **Download review (PDF)** and Leave/Edit review. Don't add dashboard/history links back to the page: the sidebar covers navigation.
- `ExplanationView` accepts the nullable `Question.references` JSON directly and normalizes it: manual questions may have no references, legacy imports may use URL strings, and batch authors may store per-option metadata. Only valid HTTP(S) reference entries render; missing references must never prevent a saved result from opening. Regression check: `node --import tsx --test src/components/explanation-view.test.tsx`.
- **Explanation option letters follow the shuffle**: explanations are authored against the stored option order ("Suggested answer: C … Option A …") but every attempt shows a per-attempt shuffle, so every surface that returns or renders an explanation — `/api/attempts/answer`, `/api/mobile/attempts/answer`, `/api/mobile/attempts/[attemptId]`, `/results/[attemptId]` and the results PDF — passes it through `explanationForDisplay(text, type, authoredOptions, shownOptions)` ([src/lib/explanation-format.ts](src/lib/explanation-format.ts)), which rewrites "Option C" / "Suggested answer: C" / "Options A and D" to the letters the taker sees (letters are case-sensitive capitals; ORDERING is left alone), and drops authoring notes that cite a local file ("Source: CCAR-F_passquestion.pdf, question 48." — URL sources stay). Never send `question.explanation` raw to a learner. `ExplanationView` and the PDF split long explanations with `explanationParagraphs()` (answer lead alone and bold, a new paragraph per "Option X …", at most ~3 sentences each; authored line breaks win). Tests: `node --import tsx --test src/lib/explanation-format.test.ts`.
- **Question types**: the runner renders SINGLE (MCQ), MULTI (multiple select — when `correct` has N > 1 ids the runner shows "Select TWO answers", fed by `selectCount` from `exam/[attemptId]/page.tsx`), TRUE_FALSE and ORDERING (sequencing). HOTSPOT is still deferred. **Sequencing**: steps are shown in a fixed numbered order (Step 1…N) via `sequencingSteps()` in [src/lib/shuffle.ts](src/lib/shuffle.ts) — never the per-attempt shuffle — so answers read like "5 → 3 → 2 → 4 → 1". Author steps out of order with ids `'1'…'N'` and `correct` = the right sequence; a question authored already in order gets a stable per-question shuffle. The exam page, results page and PDF must all call `sequencingSteps(options, correct, questionId)`.
- **Runner labels** (keep them): **Flag for review**, Review Screen with "Summary of reviews and completed" (Completed / Flagged for review / Incomplete), **Review All** / **Review Flagged** / **Submit Exam** (Exam mode keeps the Time Remaining countdown — h:mm:ss from `Exam.durationMinutes`, e.g. CCAO-F 2:00:00 — and auto-submit). The practice answer box and the results answer-key box show the domain as an "Exam domain" chip.
- **Results PDF** (also attached to the `EXAM_RESULT` email): `GET /api/results/[attemptId]/pdf` ([src/lib/pdf/attempt-report.ts](src/lib/pdf/attempt-report.ts), pdf-lib) — score, per-domain breakdown, and every question with domain, options (correct + taker's pick), sequences, explanation and references. Same access rule as `/results/[attemptId]` (owner or matching `gt` guest cookie). Helvetica is WinAnsi-only, so text goes through `clean()` (→ becomes ->).
- `Attempt.responses` is `Json` shaped as `Record<questionId, { answer: string[]; flagged?: boolean; timeSpent?: number }>` (see [src/lib/attempts.ts](src/lib/attempts.ts) `Responses` type). There is **no AttemptAnswer table** — flags, answers, and per-question timing all live in this JSON blob.
- Server-side timing for Exam mode comes from `Attempt.expiresAt` set at start. The page recomputes remaining seconds from `expiresAt - now()`. Submit also recomputes the score from responses + question definitions in [src/lib/attempts.ts](src/lib/attempts.ts) `scoreAttempt()` — never trust client-reported correctness.
- **Autosave** flushes the in-memory responses every 15s through `/api/attempts/autosave` if the runner has dirty state. There is also a `beforeunload` warning. Resume is automatic — visiting `/exam/:id` for an unsubmitted attempt rehydrates from `attempt.responses`.
- **One practice exam per certification, drawn from a domain-weighted pool** ([src/lib/question-pool.ts](src/lib/question-pool.ts)). Every attempt — practice, exam mode, teaser, "Retake exam" — calls `drawAttemptQuestions()` (signed-in starts go through `createAttempt()` / `resumeOrCreateAttempt()` in [src/lib/start-attempt.ts](src/lib/start-attempt.ts)), which apportions `Exam.questionCount` seats across `Exam.domains` weights (largest remainder; a short domain's seats are re-apportioned to the others; questions whose `domain` matches no blueprint name only fill leftover seats). Titles lead with the code and end with a short name ("AWS SAA-C03 Practice Exam in Singapore | Solutions Architect", max 66 characters, never cut mid-word), CompTIA leads with the name ("CompTIA Security+ SY0-701"), and CCAR-F also carries "CCA-F" (`ALSO_KNOWN_AS`). Product `h1`s go through `headingWithCode()`. Both product pages have certification-specific FAQs (`src/lib/product-faqs.ts`), BreadcrumbList JSON-LD and `RelatedCerts` links; `/vendors` lists every certification. "-p2" and higher leftover exams are noindex and out of the sitemap (`isExtraVariantSlug()`). **Search Console hygiene**: links into robots-blocked areas (`/checkout/` buy buttons incl. `MobileBuyBar`/`VoucherUpsell`, `/user-dashboard/` cards on `/p/support`) carry `rel="nofollow"`; an exam page with nothing on sale uses the `/og/site` card (never `/og/product/<slug>`, which only renders for a product on sale), and `/og/product/<known exam or product slug>` 308s to `/og/site` instead of 404ing; `GET …/teaser` is one 308 straight to the selling product page. Homepage meta is `HOME_SEO`; the deploy seed replaces a stored `SITE_HOME_*` value only while it still equals `LEGACY_HOME_SEO`. Meta and on-page copy use "<code> practice exam in Singapore" / "<code> exam voucher in Singapore" plus the full certification name; the Exam Voucher page builds its meta on render with `buildVoucherSeo()`, and both product pages carry a short bolded-keyword section (`components/product/seo-copy.tsx`, ~1–2% density — don't pad it further). ### Payments / fulfillment
- **Four providers**: PayPal (in-page buttons), Stripe (Checkout redirect), HitPay (redirect — card/Apple Pay), and PayNow QR (manual verification).
- **Store currency is USD** — `STORE_CURRENCY` in [src/lib/currency.ts](src/lib/currency.ts). `Bundle.price`/`priceVoucher` are USD cents and PayPal/Stripe/HitPay charge in USD; `formatPrice()` defaults to it. Never hard-code a currency in a create-order route. PayNow is the exception: SGQR only carries SGD, so [api/paynow/create-order](src/app/api/paynow/create-order/route.ts) converts at the **live USD→SGD rate** from `getUsdToSgdQuote()` in [src/lib/fx.ts](src/lib/fx.ts) (ECB via Frankfurter, then exchangerate-api; cached 1h in memory; the rate and source are snapshotted in the order's `providerPayload.fx`) and answers 503 `paynow-fx-unavailable` when no rate is known. ### Data model invariants
- **Bundle is the unit of sale.** `Exam` has no price columns; only `Bundle.price` (fixed US$20) and `Bundle.priceVoucher` matter. Don't add per-exam pricing back — it will diverge from the catalog UI and `fulfillOrder`.
- `Bundle` membership is the source of truth for "which exam is this cert's practice exam" (the PRACTICE item). Catalog cards show `"{pool}-question pool · {n} per attempt"` via `poolCardLabel()` in [src/lib/bundle-contents.ts](src/lib/bundle-contents.ts).
- `Exam.poolExamId` marks a retired variant; never publish such a row or add it back to a product. Variant rows are kept so old attempts, orders and entitlements resolve.
- `Entitlement` unique on `(userId, examId, tier)` — same exam can have multiple tiers granted.
- `Question.status` is `DRAFT | PUBLISHED | ARCHIVED`. Public reads and the attempt draw filter by `PUBLISHED`. **Human-authored questions auto-publish** (Add manually, CSV import with a blank status) — there is no "Publish immediately" checkbox. **AI-generated and agent-added questions publish too** (after validation and, for the generator, the AI answer-key check) — there is no review queue. Unpublish sets ARCHIVED (labelled "Unpublished"). DRAFT is written only by the AI Q&A Generator's **Review first** mode ("Awaiting review", published by hand — see AI generation); CSV import still maps it to ARCHIVED.
- `Question.isTeaser` is legacy: the teaser now draws from the whole pool (size pinned at 10 — see teaser flow above).
- `Question.options` is `Json` shaped as `[{id, text}]`. `Question.correct` is `Json` shaped as `string[]` of option ids. There is **no AnswerOption table** — keep these JSON shapes consistent across seed, generator, and runner.
- **CCAR-F presentation additions**: the normal boot seed calls `importCcarFoundationsPptx()` after pool consolidation to append the 57 reviewed, rephrased questions in `src/lib/seed/ccar-foundations-pptx-questions.ts`. Stable IDs and the `manual:ccar-f-pptx-2026-11-13` provenance tag make this create-only: existing questions, imported-row admin edits/unpublishing, and exam settings survive. The importer verifies the canonical pool's code, vendor, domains, and identity; it does not invoke the older replacement seed. Preview the complete answer review with `npx tsx scripts/import-ccar-foundations-pptx.ts`; `--apply` requires an existing verified bank. Source questions 13/18/47 are unavailable; blurred slide 48 was not reconstructed. - `AdminLog` is written by the AI generator. Add entries when adding admin mutations.

## Things to watch out for

- **Keep the repo root for config and source only.** Root-level images, decks (`.pptx/.docx/.xlsx`) and `/artifacts/` are git-ignored; save debug screenshots in the scratchpad, README images in `docs/images/`, and source material in the ignored `reference/`.
- **Postgres host port 55432**, not 5432 (system Postgres collision). Keep `docker-compose.yml` and `.env` in sync.
- **`--legacy-peer-deps`** is required for `npm install` because `next-auth@5.0.0-beta.25` and a few Radix peers don't yet declare React 19. Don't drop the flag.
- **Edge runtime**: never import `argon2`, `pdf-lib`, `@anthropic-ai/claude-agent-sdk`, `nodemailer`, or `@prisma/client` from [src/proxy.ts](src/proxy.ts) or any file it imports. Use `auth.config.ts` for the edge-safe shape.
- **Prisma schema** must use multi-line block syntax — Prisma rejects `enum X { A B }` on one line.
- **`(session.user as any).{id,role}`** casts are intentional — NextAuth's default `User` type doesn't include them. Add a module augmentation if you want to remove the casts.
- **`useSearchParams()` requires a `<Suspense>` boundary** at the page level for Next 15 build to succeed (see [src/app/login/page.tsx](src/app/login/page.tsx) for the pattern).
- **MailHog** catches OTP and purchase emails in dev — http://127.0.0.1:8025. SMTP failures are swallowed, so registration won't error if mail is down but the user also won't see the code.

## Deployment

Coolify-ready via [Dockerfile](Dockerfile) (multi-stage, Next standalone). Container runs `prisma migrate deploy` before `node server.js` on boot. Coolify auto-deploys on push to `main` (~1–2 min); there is no SSH/exec into the container. See [README.md](README.md) for the env var checklist.

**Migrations run in the Docker build, before `next build`** — the build pre-renders ISR pages (homepage, catalog) against the production database, so a new column would otherwise fail the build (`column … does not exist`, a `digest` in the Coolify log) and the boot-time migrate would never run. This blocked every deploy from 22 Oct 23:14 to 23 Oct. Keep migrations backward compatible: the old container serves until the new one is healthy.

**Boot runs `prisma/seed.ts` before the server** (Dockerfile CMD), so anything the seed imports must exist in the runner image — `src/lib` is copied in for that. If a deploy "succeeds" in GitHub but the site never changes, suspect the boot seed crashing (it once failed on a missing `../src/lib` import and blocked every deploy for a day). Page text the seed creates is only refreshed while it is still the original placeholder; admin edits win after that.

Env vars are only for infrastructure: `DATABASE_URL`, `NEXTAUTH_URL`/`NEXTAUTH_SECRET`, `SETTINGS_KEY` (settings encryption — rotating it orphans stored secrets), `APP_URL` (used to build payment redirect/webhook URLs). Payment/email/OAuth credentials are NOT env vars — they're managed in-app under `/admin-dashboard/settings/*`. Keep `NEXT_PUBLIC_TEST_PAYMENTS` unset in production.

## Seeding a new exam bundle to production

CKAD and CKA are the canonical templates. Coolify auto-deploys on push to `main`; there is no SSH/exec to the container — production seeding goes through a one-shot admin API endpoint.

For every new bundle `xyz` (mirror [src/lib/seed/ckad-questions.ts](src/lib/seed/ckad-questions.ts) and friends):

1. **Idempotent seed module** `src/lib/seed/xyz-questions.ts` — upserts vendor/exams/bundle; deletes + recreates questions tagged `generatedBy: 'manual:xyz-seed'`.
2. **CLI shim** `prisma/seeds/xyz.ts` — invokes `seedXyz(db)` for local runs (`npx tsx prisma/seeds/xyz.ts`).
3. **Admin endpoint** `src/app/api/admin/seed-xyz/route.ts` — admin-gated, writes an `AdminLog` entry (clone [src/app/api/admin/seed-ckad/route.ts](src/app/api/admin/seed-ckad/route.ts)).
4. **Catalog entries** in [prisma/seed.ts](prisma/seed.ts) — add the exam to `EXAMS` and the bundle to `BUNDLES` so `npm run db:seed` on a fresh DB also registers the rows. Notes:
   - `BUNDLES` membership is what keeps a seed-made bundle published: `seededSlugs` is derived from it, and any bundle *not* in the list (and with no `createdById`, i.e. not made in the admin dashboard) has both products taken off sale on every deploy.
   - The seed refreshes title/description/`priceVoucher`/items from `BUNDLE_SPECS` on every deploy **unless** an admin edited them (AdminLog `bundle.update`, `voucher.update`, `bundle.question_bank` on that bundle) — admin edits win.
   - Uniform `${slug}-p1..-pN` variants **that have a voucher tier** can use the `buildMultiVariantBundles()` spec list instead; it always appends a VOUCHER item, so practice-only bundles must be hand-written. Either way `BUNDLE_SPECS` is normalised by `singlePracticeExam()` and folded by `consolidateExamPools()`, so new certs should just author ONE exam (`${slug}-p1`) whose questions are tagged with the blueprint domain names, and add the official weights to `src/lib/exam-blueprints.ts`.
   - Add an entry to `VENDOR_EXAM_CODE_OVERRIDES` whenever the vendor's exam code isn't the slug-minus-vendor-prefix uppercased — otherwise the variant recode loop rewrites your exam codes on **every** deploy.
   - `published`, `questionCount`, and `code` are deliberately excluded from the exam upsert's `update` clause (prod admins are authoritative), so `HIDDEN_EXAM_SLUGS` and the initial question count only take effect on **create**. Get them right on the first deploy. `domains` is also skipped once `Exam.domainsVerifiedAt` is set (blueprint/admin owned).
5. `git push origin main` and wait ~1–2 min for Coolify to redeploy.
6. **Confirm the new build is live** before seeding. An *existing* seed endpoint keeps answering 200 with the OLD code until Coolify finishes, so "it returned 200" proves nothing. Poll the site for something only the new commit renders, or pass the expected exam slugs to the script (step 7), which fails with exit 4 if they are missing.
7. Seed production from this machine with the script (CSRF → login → session check → POST):

```bash
npm run seed:prod -- xyz                      # POST /api/admin/seed-xyz
npm run seed:prod -- ccao-foundations anthropic-ccao-foundations-p4   # + assert slugs present
```

Credentials:
- The script reads `PROD_ADMIN_EMAIL` / `PROD_ADMIN_PASSWORD` from the shell, then from the git-ignored `.env` (also excluded by `.dockerignore`). It never prints the password or puts it on a command line.
- **Never use `ADMIN_PASSWORD` for production.** It is the LOCAL dev admin's password and does not match prod.
- A wrong password still returns HTTP 302 from `/api/auth/callback/password`, so the script checks `/api/auth/session` for `role: ADMIN` and stops after ONE failed attempt (exit 3). Don't retry in a loop — ask the user.
- If `PROD_ADMIN_PASSWORD` is empty or wrong, **don't guess**. Fallback that needs no stored secret: open `https://exams.tertiaryinfotech.com/login?next=/admin-dashboard` in the Playwright browser, let the user type their own password there, poll `/api/auth/session` until `role === 'ADMIN'`, then run `fetch('/api/admin/seed-xyz', { method: 'POST' })` inside the page and close the browser afterwards. (Equivalent manual route: the user pastes that `fetch(...)` into DevTools while signed in as admin.)

Exit codes: 0 ok · 1 non-200 from the seed · 2 no password configured · 3 login failed · 4 expected exam slug missing (deploy not live yet — wait and re-run).

Notes:
- The credentials provider id is **`password`** — POST to `/api/auth/callback/password`, NOT `/api/auth/signin/password` (that's the form page). The `otp` provider only accepts one-time codes. Session cookie: `__Secure-authjs.session-token` (the script's cookie jar handles it).
- A 404 right after push means a *new* route hasn't rolled out yet — retry after the deploy completes. A 200 with `{ ok: true, exams: [...] }` listing the expected slugs confirms the seed ran.
- Seeds are idempotent (delete-and-recreate by `generatedBy` tag); safe to re-run.
- The product page shows one practice exam; legacy variants in a seed are folded into it automatically.
